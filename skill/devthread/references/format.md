# DevThread state format

State lives in the project root's `.devthread/`: `config.json` with `schemaVersion: 1`; `PROJECT.md`, `REQUIREMENTS.md`, `ARCHITECTURE.md`, `ROADMAP.md`, and `DECISIONS.md`; `tasks/`; and `reports/`. Existing `.devmap/` state is accepted without moving or replacing files. Both state paths together are an error and must not be merged automatically. The scripts validate this format. Unknown metadata fields should be preserved; unknown schema versions must not be changed.

Task filenames and IDs match `TASK-[0-9]{3,}`. Requirement headings use `## REQ-001: Title`. Add new IDs after the highest existing number; never recycle IDs. Task frontmatter requires `id`, `title`, `status`, `priority`, `depends_on`, and `requirements`. Use simple strings or JSON-quoted strings and inline lists such as `[REQ-001]` or `["REQ-001"]`; complex YAML is unsupported. The body requires `Goal`, `Scope`, `Acceptance Criteria`, `Relevant Files`, `Evidence`, and `Notes/Blockers` headings.

Statuses are `backlog`, `ready`, `in_progress`, `blocked`, `review`, and `done`; priorities are `low`, `medium`, and `high`. A ready task's dependencies must all be done. Completion is an explicit reviewed status update, never an automatic result of code changes. Evidence level is separate from status: `verified` requires relevant recorded passing checks or review, `likely` has source support without verification, `missing` follows a bounded unsuccessful search, `blocked` names an impediment to obtaining evidence, and `unknown` covers insufficient or conflicting information. Source inspection alone does not prove runtime behavior.
